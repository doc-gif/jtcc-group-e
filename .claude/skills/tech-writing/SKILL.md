# 技術文書の書き方（tech-writing）

このリポジトリの文書（`docs/*.md`・`AGENTS.md`・`README.md`）、Issue と PR の本文、Issue のコメントを書くときに従う。読者は**作業者エージェント**（クラウド・ローカルの Claude Code）と担当者（@doc-gif）。作業者は本文を仕様として読み、そのまま実装する。曖昧な語は、ズレた実装になる。

要点は 3 つ。

1. **用語を固定する。** 下の用語集の語だけを使う。とくに「デモ」「デモ用」「ピッチ用」「本番」を単独で使わない。
2. **1 文 1 内容、能動態、短く書く。** 読者が推測しないで済む形にする。
3. **Issue・PR は決まった節の順で書く。** 受け入れ条件は検証できる形にする。

## 1. 用語集（担当者の決定 2026-09-26、Issue #135。これを正とする）

同じ 1 つのアプリ（同じビルド）に 2 つの入口がある。画面・データ・規則を語るときは、必ずどちらの版の話かを書く。

| 用語 | 意味 | 対象者 | 入口 | サンリオ IP |
| --- | --- | --- | --- | --- |
| **限定公開アプリ**（ピッチ用） | 関係者だけが使う版。ホストが部屋を作り招待する | 関係者・ピッチの場 | ホスト用リンク（`#/host/<キー>`）・招待リンク | **IP の許諾あり**（キャラクターの絵などを使ってよい。範囲は担当者が Issue で個別に決める） |
| **一般公開アプリ** | LP から誰でも入れる版。毎時 00 分・30 分に自動で始まる部屋 | 一般の利用者 | LP の固定リンク（例 `#/demo`） | **実写真のサンリオ商品画像だけ**使える。キャラクターのイラスト・ロゴ・アセットは不可 |

規則:

- 「デモ」「デモ用」「デモ用リンク」「ピッチ用」「本番」を単独で使わない。上の 2 語のどちらかで書く。
- 「本番」は**本番環境（公開先）**の意味だけに使う。例: 「本番公開」「本番の Supabase」「本番の URL」。「本番の動き」「本番化」のようにアプリの版や段階の意味では使わない。
- 「キャラクターの絵・サンリオのアセットはアプリ・リポジトリ・プレビューに入れない」の規則は、**一般公開アプリと、両方の版で共有される画面・部品・リポジトリの素材**に適用する。限定公開アプリだけに出る画面・素材は、担当者の許諾の範囲で使える。

### 関連する語（これも固定する）

| 用語 | 意味 | 使わない言い方 |
| --- | --- | --- |
| **ピッチモード** | 限定公開アプリで、ホストが部屋ごとにオンにする切り替え。オンの間は各ラウンドで 1 人に目玉を確定する | 「ピッチ用（の切り替え）」「ピッチ用デモ」 |
| **端末内の模擬ルーム** | Supabase の設定がない開発サーバー・単体テスト・E2E（`lastpiece_room_force_demo=1`）で、同じブラウザのタブの間だけで動く模擬サーバー（`MockRoomServer`）のルーム。どちらの版でもない、開発と検査のための代わり | 「端末内デモ」「1 台デモ」（コード上の識別子 `demoTransport`・`force_demo` はそのまま） |
| **説明用の架空データ** | カタログ・価格・在庫・友だち（ゆい・さき）・棚の数字など、実在しない見本のデータ | 「デモ例」「デモデータ」「デモの〜」 |
| **デモコイン** | アプリ内の架空の通貨の名前（画面・Figma のマスターの表記） | 「コイン（デモ）」。名前を変えるかは担当者の判断（#135） |
| **審査用の操作** | マイページの「次の 1 回を目玉確定にする」など、動作を確かめるための切り替え | 「デモ操作」（画面の見出しの名前として書くときは「マイページの「デモ操作」」と引用する） |
| **本番環境** | GitHub Pages の公開先（最新 URL と `/versions/vX.Y.Z/`）と、本番の Supabase `lastpiece-pitch` | 「本番」を版・段階の意味で使うこと |
| **確認用プレビュー** | PR ごとに `doc-gif/jtcc-group-e-preview` に自動配布されるサイト | 「テスト環境」「ステージング」 |
| **LP** | ランディングページ `doc-gif/lastpiece-lp`（別リポジトリ） | — |
| **担当者** | @doc-gif。判断と許諾を出す人 | 「オーナー」「ユーザー」 |
| **作業者** | Issue を担当するエージェント（`cloud #N` / `local #N`） | 「AI」「ボット」（アプリのボットと混ざる） |
| **マネージャー** | `docs/OPERATIONS.md` の定期実行 | — |

言い換えの例:

| 前 | 後 |
| --- | --- |
| デモ用リンク（LP）とピッチ用リンクを分ける | 一般公開アプリ（LP から）と限定公開アプリ（ホスト用リンク）を分ける |
| ピッチ用の実物グッズ写真 | 限定公開アプリの実物グッズ写真 |
| 一般公開のデモに写真を出す | 一般公開アプリに写真を出す |
| デモの部屋・ピッチの部屋 | 一般公開アプリの部屋（`kind = 'demo'`）・限定公開アプリの部屋（`kind = 'pitch'`） |
| LP → デモの数字 | LP → 一般公開アプリの数字 |
| 端末内デモでは写真を読まない | 端末内の模擬ルームでは写真を読まない |
| 棚 2/9 はデモ例 | 棚 2/9 は説明用の架空データ |
| 本番の動きは変えない | 限定公開アプリの動きは変えない |

固有名詞（Figma の画面名「友達と回す（デモ）」、GitHub の Milestone 名、コードの識別子、画面に出ている文言）は、そのままの名前で引用する。名前を変えるときは、その持ち物の担当（Figma・Milestone は担当者、コードは実装の Issue）で変える。

## 2. 書き方の原則（Google Technical Writing One / Two の要点）

### 語

- **用語は 1 つに決めて、文書の中で一貫して使う。** 同じものを「ルーム」「部屋」「セッション」と呼び分けない。新しい用語は初出で定義する。
- **略語・記号は初出で展開する。** 例: 「LP（ランディングページ）」「RLS（Row Level Security）」。この文書の用語集にある語はそのままでよい。
- **代名詞・指示語を避ける。** 「これ」「それ」「上記」「同ファイル」より、名前を書く。「これを直す」ではなく「`docs/PRODUCT.md` の写真の行を直す」。
- **曖昧な語を使わない。** 「デモ」「本番」「いい感じに」「適宜」「必要なら」「など」を単独で使わない。「など」を使うときは、列挙が例であると分かる文にする。
- **数値・ファイル名・コマンド・識別子はバッククォートで書く。** `pnpm verify`、`docs/OPERATIONS.md`、`267:8198`。

### 文

- **能動態。主語を書く。** 「マージされる」ではなく「Bot がマージする」。「確認が必要」ではなく「担当者が確認する」。
- **1 文 1 内容。** 「〜し、〜して、〜する」を 3 つに分ける。目安は 1 文 60 字以内。
- **強い動詞を使う。** 「〜を行う」「〜の実施」より「〜する」。
- **条件は先、結果は後。** 「`in-progress` が付いていたら、手を出さない」。
- **時点の事実には時刻を付ける。** 「（2026-09-26 06:25 UTC 時点）」。変わる事実（main の SHA・本番の版・PR の状態）は文書に書かない（`AGENTS.md`「情報の鮮度」）。
- **否定は 1 回まで。** 「〜しないとは限らない」を避ける。
- **記録は過去形、規則は現在形。** 「#41 でマージした」「Bot がマージする」。

### 段落と構成

- **段落の先頭に要点。** 最初の文で、その段落が何を言うかを書く。理由・例は後ろ。
- **1 段落 1 テーマ。** 3〜5 文に収める。
- **読者に必要な前提を先に書く。** 作業者が読む文書は、冒頭に「何のための文書か」「誰が読むか」「先に読む文書」を書く。
- **文書の冒頭に要約。** 長い文書は、最初の段落で全体を 3 行にまとめる。
- **見出しは名詞句か「〜するとき」。** 見出しだけ読めば構成が分かるようにする。
- **並列の項目は箇条書き。順序のある手順は番号付き。** 1 手順 1 操作。手順の後に、成功したときの状態を書く（「〜が出る」「〜になる」）。
- **条件・選択肢・対応表は表。** 3 つ以上の条件を文で書かない。列の見出しに単位・意味を書く。
- **表・図・コードの前に 1 文の説明。** 何を見せる表かを先に書く。
- **強調は最小限。** 太字は 1 段落に 1 か所まで。

### 例

前:

> デモの写真は許諾の範囲の確認まで出さないので、フラグで無効にしておく。

後:

> 一般公開アプリでは、実写真のサンリオ商品画像だけを出せる（用語集）。写真を出す時期は #58 の子 Issue で決める。それまでは写真の切り替えを無効のままにする。

## 3. Issue 本文の書き方（テンプレート `.github/ISSUE_TEMPLATE/task.md`）

Issue は作業者への仕様書。節の順は固定する。マネージャーは「作業者への指示（プロンプト）」の節をそのままセッションの指示に使う（`docs/OPERATIONS.md`）。

| 節 | 書くこと | 書かないこと |
| --- | --- | --- |
| 冒頭 | 親 Issue（`親: #N`）。担当者の決定は「担当者の決定（日付）: 〜」と引用 | 状況（着手・進捗。ラベルとコメントに置く） |
| 目的 | 何を、誰のために、なぜ変えるか。1 段落 | 実装の手順 |
| 用語 | この Issue で使う語が用語集のどちらの版か。用語集に無い語は定義する。例: 「この Issue の「部屋」は一般公開アプリの部屋（`kind = 'demo'`）」 | 用語集と違う言い方 |
| 受け入れ条件 | 検証できる形の箇条書き（チェックボックス）。「〜が出る」「テスト `x.test.ts` が通る」「`docs/X.md` に〜の行がある」 | 「使いやすい」「きれいに」などの主観 |
| 触ってよいファイル・資源 | パスのパターン、Figma の node、Supabase のテーブル。触ってはいけないものも書く | — |
| 依存 | 先に終わる Issue、必要なロック（`lock:*`）、担当者の返事待ち | — |
| 作業者への指示（プロンプト） | 手順と注意だけ。仕様は上の節を参照させる。検証コマンド、Ready の前にすること、質問の仕方（`needs-owner`） | 仕様の本文（上の節に書く）、規則に反する指示（他リポジトリへの push・秘密の出力・本番公開） |

受け入れ条件の書き方:

- 前: 「デモで写真が出る」
- 後: 「限定公開アプリの結果画面で、自分が当てた品の写真が出る（`e2e/room.spec.ts` に確認を追加）」

意味が変わる修正は本文を直接直さず、コメントで提案して `needs-owner` を付ける。`in-progress` の Issue の本文は書き換えず、コメントで作業者に知らせる。

## 4. PR 本文の書き方（テンプレート `.github/pull_request_template.md`）

- **1 行目**に `Closes #N` か `Refs #N`（`docs/OPERATIONS.md`「Issue と PR の結びつき」）。
- 「目的と変更後の動作」は、利用者から見た変化を先に、実装の要点を後に書く。どちらの版の話かを書く。
- 「検証」は、実行したコマンドと結果を書く。実行していない項目は空欄のままにせず「未実施（理由）」と書く。
- 「影響・残る制約」は、変えていないこと（本番公開はしていない、保護設定は変えていない）も書く。
- Copilot の指摘は、対応（修正した commit）か根拠（誤検知・承認済み）を書いて解決する。
- モデル名を書かない。秘密・鍵・ホスト用キー入りのリンクを書かない。

## 5. コメントの書き方（Issue・PR）

| 場面 | 形 |
| --- | --- |
| 着手 | `[cloud #N] 着手します。ブランチ: …、触るファイル・資源: …` |
| 途中経過 | 1 行。何が終わり、次に何をするか |
| 質問 | `needs-owner` を付け、@doc-gif に。選択肢を表にし、作業者のおすすめを 1 つ書く。返事を待つ間に進める部分も書く |
| 完了 | `#PR をマージ（内容 1 行）` |
| 末尾 | 空行・`---`・`_Generated by [Claude Code](https://claude.ai/code)_` |

## 6. 点検の手順

文書・Issue・PR を書き終えたら、次を確かめる。

1. 曖昧語を探す。

   ```sh
   grep -n "デモ\|ピッチ用\|本番" docs/*.md .github/ISSUE_TEMPLATE/*.md
   ```

   「本番」は本番環境の意味だけか、「デモ」「ピッチ用」は固有名詞の引用だけかを見る。
2. 代名詞・指示語（これ・それ・上記・同）を名前に置き換える。
3. 1 文が 2 つ以上の内容を持っていたら分ける。
4. 受け入れ条件がすべて検証できる形か見る。
5. 変わる事実（SHA・版・PR の状態）を「現在〜」と書いていないか見る。`scripts/live-state.test.mjs` が検査する。
6. 秘密・鍵が無いか見る。`scripts/governance.test.mjs` が検査する。
