# 計測の集計（GA4・Clarity → 手動実行で Issue に 1 コメント）

LP（https://doc-gif.github.io/lastpiece-lp/ ）と一般公開アプリ（https://doc-gif.github.io/jtcc-group-e/ 。LP から来る人の入口）は同じ GA4 プロパティ（測定 ID `G-3DDS1NJZXS`）なので、**LP に入った人が一般公開アプリに進んだ割合**は GA4 で出せる。Clarity はスクロールの奥行き・デッドクリックなど「見え方」の補助。

- スクリプト: `scripts/metrics-report.mjs`（依存なし。`node scripts/metrics-report.mjs --days 7`）
- 実行: `.github/workflows/metrics-report.yml`（**手動だけ**。担当者の指示 2026-09-26。Actions → Metrics report → Run workflow、days を指定）。結果は Actions の要約と、`[metrics]` の Issue（#112）へのコメント。
- 出るもの: LP のセッション・ユーザー・**しっかり見た**（GA4 の「エンゲージのあったセッション」= 10 秒以上か 2 ページ以上）・90% スクロール・平均滞在・ページ/セッション・**一般公開アプリのページも見たセッションと割合**・一般公開アプリ側のイベント（本番公開後）。Clarity は LP と一般公開アプリそれぞれのセッション（ボット除外数）・ページ/セッション・スクロール・デッドクリック・イライラしたクリック（過去 3 日、API の上限）。

## 出せないもの（正直に）

- **1 セッションが何ページ見たか（分布）**は GA4 Data API・Clarity API のどちらでも取れない。BigQuery エクスポート（GA4 → BigQuery、無料枠あり）を有効にすれば出せる。LP は 1 ページの site なので、当面は「2 ページ目以降 = 一般公開アプリへ進んだ」とみなし、到達率で代える。
- 一般公開アプリ側のイベント（`demo_start` など）は本番公開後にしか届かない。

## 担当者の準備（一度だけ）

### GA4（主）

1. GA4 の **プロパティ ID**（数字）を控える: GA4 → 管理 → プロパティ → プロパティの詳細 → 「プロパティ ID」。
2. Google Cloud で **サービスアカウント**を作る: https://console.cloud.google.com/ → プロジェクトを選ぶ（無ければ作る）→ API とサービス → ライブラリ → **Google Analytics Data API** を有効化 → IAM と管理 → サービスアカウント → 作成（役割は不要）→ 作ったアカウントの「キー」→ 新しい鍵 → JSON をダウンロード。
3. GA4 にそのアカウントを **閲覧者**で追加: GA4 → 管理 → プロパティのアクセス管理 → ＋ → サービスアカウントのメール（`…@….iam.gserviceaccount.com`）→ 役割「閲覧者」。
4. リポジトリに入れる（Settings → Secrets and variables → Actions）:
   - 変数 `GA4_PROPERTY_ID` = プロパティ ID
   - 秘密 `GA4_SA_KEY` = ダウンロードした JSON の中身をそのまま貼る
   - ローカルなら `gh variable set GA4_PROPERTY_ID --repo doc-gif/jtcc-group-e --body <ID>`、`gh secret set GA4_SA_KEY --repo doc-gif/jtcc-group-e < key.json`
5. 鍵の JSON はチャット・Issue・PR に貼らない。ダウンロードしたファイルは登録後に削除してよい。

### Clarity（補助）

1. Clarity → 該当プロジェクト → 設定 → **データ エクスポート**（Data Export）→ **API トークンを生成**（名前は `jtcc-metrics` など）。
2. 秘密 `CLARITY_TOKEN` に入れる。変数 `CLARITY_ENABLED` = `true`（GA4 を設定しない場合でも workflow を動かすための印）。
3. 上限: 1 日 10 回、過去 1〜3 日分だけ。手動実行は 1 日 10 回まで。

### 結果を受け取る Issue

- `[metrics]` の Issue は #112。番号は変数 `METRICS_ISSUE` に入れる。無ければ Actions の要約にだけ出る。

### 初回の実行

- Actions → **Metrics report** → Run workflow（days = 7）。要約に表が出れば成功。失敗したら「取得できなかったもの」に理由が出る（権限不足なら GA4 の閲覧者追加か API の有効化が漏れている）。

## LP が 0 と出たとき

表の下に「プロパティ全体のセッション」と「多い入口」が出る。全体も 0 なら `GA4_PROPERTY_ID` が測定 ID `G-3DDS1NJZXS` のプロパティか（GA4 → 管理 → データ ストリーム → 測定 ID で確認）、LP が GA4 に送っているか、反映の遅れ（最大 24〜48 時間）を疑う。全体に来ているのに LP が 0 なら、入口の URL が `/lastpiece-lp/` と違う（例: 独自ドメイン）。

## レポートの読み方

レポートは Google のテクニカルライティングの指針（要約を先に、1 文に 1 つの内容、用語を表で定義、値に単位）で書く。各表には「定義」の列があり、数の求め方をそこに書く。

### 計算の決まり

| 値 | 求め方 |
| --- | --- |
| しっかり見た割合 | エンゲージのあったセッション ÷ LP に入ったセッション。GA4 の定義は「10 秒より長い滞在、または 2 ページ以上の表示」 |
| 90% までスクロールした割合 | scrolledUsers ÷ ユーザー。分母がユーザーなので、セッションの割合とは混ぜない |
| 平均滞在時間・表示ページ数 | 入口ページの行を**セッション数で重み付け**して平均する |
| 一般公開アプリへの到達 | GA4 はページごとにセッション数を返すので、正確な数は「下限（一般公開アプリのページ別セッション数の最大値）」と「上限（合計）」の間にある。下限と上限が同じならその値が正確 |
| Clarity の平均（表示ページ数・スクロール・デッドクリック率） | URL の行を**セッション数で重み付け**して平均する |
| Clarity のプロジェクト全体 | 次元なしで取った重複のない数。LP・一般公開アプリの列は URL 別の合計なので、同じ人が複数の URL に出るとユーザーが重複する（全体 < LP + 一般公開アプリ になることがある） |

### 判断の目安

- しっかり見た割合が低い（例: 30% 未満）→ 最初の画面で離脱している。LP の最初の画面に一般公開アプリの入口があるかを見る。
- 一般公開アプリに進んだ割合が、しっかり見た割合より大きく下がる → 導線（ボタン・QR）の位置か文言を疑う。Clarity のデッドクリックの録画で、押されたのに反応しない場所を探す。
- 自分たちのテスト閲覧は、アプリと LP の両方で `?internal=1`・localhost・確認用プレビューを送信元で除外している。
