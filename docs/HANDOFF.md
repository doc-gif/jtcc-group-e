## 5. 【新規】ネイティブアプリのような操作感（方法1: 全画面表示とジェスチャーの抑制）— **これだけを進める**
**分かったこと（F16 の PR #62、2026-09-26）**: ホーム画面のアプリにはアドレスバーがなく、iPhone では保存データも Safari と別なので、3 の案内を作るときは招待リンク・ホスト用リンクからホーム画面のアプリで入る方法も一緒に決める（PRODUCT.md の未決事項）。ヘッドレスのブラウザは抑制がなくても合成したピンチで拡大しないため、ピンチの効きは実機でだけ確かめられる。

担当者の決定（2026-09-26）: Capacitor（ネイティブ化）は**まだやらない**。Web のまま、次の範囲だけ直す。

**困りごと**: ブラウザのタブで動くので、リンクバーが出る。ピンチで画面が拡大・縮小し、ブラウザのタブ操作・端スワイプ（戻る／進む）・引っぱって再読み込みとぶつかり、ネイティブアプリの触り心地と違う。

**やること**（ブランチ例 `claude/f16-standalone`、1つの PR）
1. **ホーム画面から全画面で開く（PWA の standalone）**
   - `public/manifest.json`: `display: "standalone"`、`start_url`・`scope` を公開パス（`/jtcc-group-e/`、固定版 `/versions/vX.Y.Z/` でも壊れない相対指定）に。`theme_color`・`background_color` をマスターの色に。アイコンは既存（`icon-192.png`・`icon-512.png`・`icon-maskable-512.png`）。
   - `index.html`: `apple-mobile-web-app-capable`／`mobile-web-app-capable`、`apple-mobile-web-app-status-bar-style`、`apple-touch-icon`、`viewport-fit=cover`（セーフエリアは既存の `env(safe-area-inset-*)` を確認）。
   - 固定版（`/versions/`）とプレビューのパスで manifest とアイコンが正しく読める・保存データが混ざらない（既存の分離のテストを壊さない）。
   - Service Worker は**入れない**（版ごとのキャッシュ設計が必要なため別タスク。DEPLOYMENT.md の注意どおり）。
2. **ジェスチャーの抑制**
   - ピンチで画面全体が拡大・縮小しない: アプリの外枠に `touch-action: pan-x pan-y`（地図のドラッグなど独自の操作がある要素は必要な値に）、iOS Safari の `gesturestart`／`gesturechange` を `preventDefault`。ダブルタップ拡大も止める（`touch-action: manipulation`）。
   - 引っぱって再読み込み・端のバウンドを止める: `html, body { overscroll-behavior: none; }`（スクロールする中身は `contain`）。
   - 長押しメニュー・文字選択・タップの色: ボタンや画像に `-webkit-touch-callout: none`、`user-select: none`、`-webkit-tap-highlight-color: transparent`（入力欄・本文の説明は選べるままにしてよい）。
   - **アクセシビリティを守る**: `viewport` で `maximum-scale=1`／`user-scalable=no` を**使わない**（iOS は無視する・Android では拡大を奪う）。OS の文字サイズ設定（rem、文字200%）には必ず従う。docs/UI_UX_STANDARDS.md の全項目と既存の文字200%の UX テストを通す。
3. **「ホーム画面に追加」の案内**（ピッチで来場者に案内する）
   - 新しい画面・部品なので **Figma が先**: マスター（`267:8198`）に案内の状態（iPhone: 共有 →「ホーム画面に追加」、Android: メニュー／インストール）を追加し、ADOPTED_DESIGN に記録してから実装。担当者の確認を取る。
   - ブラウザのタブで開いているときだけ出す（`display-mode: standalone`・`navigator.standalone` で判定）。閉じられる、何度も出さない（保存はその端末だけ）。Android は `beforeinstallprompt` があればボタンで出す。
   - 招待リンクから来た人にも出せるようにする（ルームに入る前に邪魔しない位置）。
4. **テスト**: manifest の中身（display・start_url・scope・アイコン）、`index.html` のメタ、CSS（`overscroll-behavior`・`touch-action`）、ジェスチャーの抑制（Chromium で pinch 相当のイベントが既定動作にならない）、standalone のときは案内を出さない・タブのときは出す、閉じたら出ない。既存の UX・文字200%・WebKit の構成を通す。`docs/ux-reviews/<task>.json` を `pnpm ux:digest` で作る。

## 6. 【新規】複数エージェントの競合を防ぐ（マージ・リリースのキュー）
いくつものエージェントが同時に PR を出すと、次のことが起きている。
- 1つマージされるたびに、ほかの PR が `main` の取り込みと UI digest（`docs/ux-reviews/*.json` の `uiDigest`）の作り直しを求められ、CI をやり直す（auto-merge は最新の main を必須にしている）。
- STATUS.md・PRODUCT.md・ADOPTED_DESIGN.md の同じ表で衝突し、手で直す。
- 本番公開（`release-pages.yml`）は `concurrency: pages-release`（`cancel-in-progress: false`）だが、GitHub は**待機中の実行を新しい実行で置き換える**ことがあり、同時に頼むと消える。バージョン番号も手で決めるので重なりうる。
- 共有の Supabase（migration の順番）と Figma のマスターも、同時に触ると壊れる。

**やること**（ブランチ例 `claude/ops-queue`。CI の設定変更なので小さく分けて PR にする。main の保護設定の変更は担当者の確認を取る）
1. **マージのキュー**
   - 候補A: GitHub の **merge queue**（main の保護で「Require merge queue」、ci.yml に `merge_group` を追加、auto-merge.yml はキューに入れる方式へ）。各 PR が main を取り込み直す必要がなくなる。
   - 課題: UI digest はマージ後の中身で変わるため、キューの中で `check-ux-review` が落ちる。PR の head で記録した digest と、マージ後の digest の扱いを決める（例: キューの実行ではマージ結果で digest を再計算し、PR のレビュー記録は「PR の head の digest」と照合、UI の変更がほかの PR と重なったら差し戻す）。品質の門（Quality gate・UI/UX gate・全5構成）は弱めない。
   - 候補B（A ができない場合）: auto-merge を「1本ずつ、古い順」にし、Bot が自分で main を取り込んで digest を作り直して CI を回す（エージェントが手でやっていた作業を Bot に移す）。
   - どちらにするかは、GitHub のプラン・設定で使えるかを確かめてから決め、担当者に一言報告する。
2. **リリースのキュー**
   - バージョンを自動で決める（入力なしなら最新タグの patch を +1。入力があれば従来どおり検証）。
   - 同時の依頼が消えないようにする（例: 公開の依頼を Issue のラベルやファイルで積み、1本ずつ処理する。または公開する側を1人（取りまとめ役）だけにする規則を AGENTS.md に書く）。
   - 公開後の確認（Release の SHA・`deployment.json`・URL と QR）を workflow の最後で自動で出す。
3. **共有資源のロック**（規則として AGENTS.md・docs に書く。必要なら軽い仕組みを足す）
   - **Supabase の migration**: 同時に1本だけ。着手前に Issue（例: ラベル `lock:supabase`）で宣言し、適用・ファイル名合わせ・PR のマージまで持つ。CI で migration のファイル名（version）の重複・順番を検査するテストを足す。
   - **Figma のマスター**: 同時に1つの作業だけが編集する（ラベル `lock:figma-master`）。それ以外は Town v2 の自分の作業領域で作る。
   - **STATUS.md などの共通の表**: 衝突しにくい形に（例: 各タスクの記録を `docs/status/<task>.md` に分け、STATUS.md は一覧だけにする）。
4. **担当の宣言**: 着手時に Draft PR（または Issue）で担当ファイル・Figma の node・DB を書く（DESIGN.md の手順1を全タスクに広げる）。ぶつかる相手がいたら先に調整する。
5. **文書だけの PR は軽い CI で済ませる**（担当者の要望、2026-09-26）
   - いまは文書だけの PR でもブラウザのテスト8本とプレビューのビルドが毎回回る。
   - `paths-ignore` で CI 自体を止めてはいけない（必須チェックの Quality gate・UI/UX gate が「未報告」のままになり、Bot がマージできない）。
   - ci.yml の最初のジョブで変更ファイルを調べ、**すべて `docs/**` または `.github/` 以外の `*.md`** なら「文書だけ」と判定する。`AGENTS.md`・`CLAUDE.md`・`.github/**`・`.env*`・`supabase/**` など動きや規則に関わるものは「文書だけ」に含めない。コードと文書が混ざった PR は今までどおり全部の検査。
   - 文書だけのとき: 秘密の検査（`scripts/governance.test.mjs` など）・`node scripts/check-ux-review.mjs`・（必要なら）リンク切れの検査だけを回し、Quality gate と UI/UX gate を成功で報告する。ブラウザのテスト・Preview build・公開・単体テストとビルドは飛ばす。
   - 判定を間違えて本来の検査を飛ばさないことをテストする（判定のスクリプトに単体テスト: 文書だけ／コードが混ざる／`AGENTS.md`／`.github` の変更）。品質の門は弱めない。
6. 文書: AGENTS.md・docs/DEVELOPMENT.md・docs/DEPLOYMENT.md・docs/FAST_FEEDBACK.md を新しい流れに合わせる。


## 7. 【新規】デモ用リンク（LP）とピッチ用リンクを分ける
担当者の決定（2026-09-26）。いまは「ホストが作らないとルームがない」設計だが、リンクの種類で仕様を変える。

| | ピッチ用（今のまま） | デモ用（新規・LP に載せる） |
| --- | --- | --- |
| 入口 | ホスト用リンク `#/host/<キー>` でホストが作る → 招待リンク | 固定のデモ用リンク（例: `#/demo`）。誰でも入れる。キー不要 |
| 開始 | ホストが開始・予約（1/3/5/10分）・ピッチ用 | **毎時 00分・30分に自動で始まる**。ホストはいない（サーバーが回す） |
| 人数 | ホスト以外に2人以上（F13） | 2人は必要だが、**足りない分はボットが参加して埋める** |
| 回ごと | 部屋の続き | **毎回リセット**（在庫・コイン・結果を初期状態に戻して次の回へ） |
| 写真 | ピッチ用の実物グッズの写真（F15-2） | 担当者は「出す」を希望。**ただし許諾は「ピッチ・関係者だけ」なので、許諾の範囲が一般公開のデモにも広がったと担当者が確認してから有効にする**（それまでオリジナルのイラスト。フラグで切り替え） |

**このタスクは実装まで行う。** 下の方針に沿って、Figma → サーバー → アプリ → テスト → PR → 本番公開 まで進める。

**設計の方針**
- **Figma が先**: デモ用の入口・次の回までの待ち（「次は 14:30 から」）・ボットの表示・回の終わりとリセットの画面をマスターに追加し、担当者の確認を取ってから実装。
- **サーバー（Supabase、新しい migration）**:
  - 部屋に種類（`kind`: `pitch` / `demo`）を足す。デモの部屋はホストなし・キー不要で `lp_join_demo`（仮）から入る。上限100人を超えたら次のデモの部屋を作って振り分ける。
  - 30分ごとの自動開始: 既存の予約（F07 の `lp_fire_due`。部屋をロックするすべての RPC の最初に実行）を使い、回が終わったら次の 00/30 分を自動で予約し直す。誰もいない時間は何もしない（次に誰かが来たときに、その時点の次の枠を予約）。必要なら pg_cron（拡張の有効化は担当者の確認）。
  - 人数が足りないとき: 開始の時点でホスト以外が2人未満なら、足りない分の**ボット**の席を入れて抽選に参加させる（在庫・確率は同じ規則。結果も同じ規則で公開）。ボットは名前に「（ボット）」を付けるなど**本物の人のふりをしない**（アプリの方針「実在の多人数接続を装わない」を守る）。人の参加者が0人の回は始めない。
  - 回の終わりのリセット: 次の回の前に在庫・コイン・結果を初期状態へ（サーバーの回の結果は残さない。個人の「自分の履歴」は端末側に残る）。
  - ピッチの規則（ホストだけが作る・ホスト以外2人以上・ホスト用キー）は**変えない**。RLS・権限・ロックの順（部屋 → 会員・在庫・ラウンド）・`lp_fire_due` を先に実行、の決まりを守る。
- **アプリ**: 入口のリンクで部屋の種類を選ぶ。デモでは次の回までの秒読み、ボットの表示、リセット後の「もう一度参加」。LP のサイト（`jtcc-lastpiece-lp`）にデモ用リンクと QR を載せる（LP 側の作業は別リポジトリ）。
- **注意**:
  - 匿名ログインの上限（1つの IP から1時間60件）。LP から大勢来ると当たるので、担当者に上限の見直しを確認。
  - デモの部屋は誰でも入れるので、名前の荒らし対策（名前の規則は既存、必要なら通報・非表示は別タスク）。
  - 写真を出すかは上の条件のとおり。
- **テスト**: PGlite（デモの部屋の作成・振り分け、00/30 分の自動予約と再予約、ボットの補充、リセット、ピッチの規則が変わらないこと）、模擬サーバーとの同等性、状態層・画面のテスト、E2E（デモの流れ）。実 DB へ適用して md5・権限・動作・advisors を確認。

**やること（順番）**
1. Figma: デモ用の画面（入口、次の回までの待ち、ボットの表示、回の終わり・リセット）をマスターに追加 → 担当者の確認。
2. Supabase: 新しい migration（部屋の種類、`lp_join_demo`（仮）、00/30 分の自動予約と再予約、ボットの補充、回ごとのリセット）→ 実 DB に適用 → 確認。
3. アプリ: デモ用リンク（`#/demo` など）の画面、秒読み、ボットの表示、「もう一度参加」。写真は許諾の範囲の確認まで無効（フラグ）。
4. テスト・文書（SHARED_OPENING_CONTRACT・PRODUCT・STATUS・`docs/SQL_MIGRATION_<task>.md`・UX レビュー記録）。
5. PR → CI 緑 → Bot のマージ → 本番公開 → デモ用リンクの URL と QR を担当者へ（LP に載せる用）。

## 8. 【新規】ハンドルを指で丸くなぞって回す
担当者の要望（2026-09-26）: いまはハンドルの**タップ**で1回転進むだけ。**指でハンドルを円を描くようになぞって回す**体験を足し、本物のガチャガチャを回す手触りに近づける。

**経緯**: 以前は「なぞって回す」があったが、F11 でマスター（T08 `267:8348` など「右のハンドルをタップ」）に合わせて外した。今回は担当者の新しい指示なので、**Figma のマスターを先に直して**から実装する（マスターに「なぞって回す」の案内と状態を足す）。

**やること（実装まで行う）**
1. Figma: T08 の回す画面（`267:8348`〜`267:8374` の回転 1〜3）に、なぞる案内（例: 「ハンドルを丸くなぞって回そう」＋円の矢印）と、なぞっている途中の見た目（ハンドルが指に合わせて回る・1周で「カチッ」）を足す → 担当者の確認。
2. アプリ（`src/components/Machine.tsx`・`src/screens/Spin.tsx` 周り）:
   - Pointer Events で、ハンドルの中心からの角度の変化を積み上げ、**1周（360°）で1回転**として今の「1回転進む」と同じ処理を呼ぶ。時計回り・反時計回りのどちらも1周で数えるか、時計回りだけにするかを決める（案: どちらでも可、逆回しは打ち消さない）。
   - 回している途中はハンドルの絵を指の角度に合わせて回し、1周ごとに軽い演出（`navigator.vibrate` が使える端末なら短い振動、音は既存の設定に従う）。
   - 指がハンドルから少し外れても続くように（`setPointerCapture`）。速く回しすぎても1回に1回転まで（3回転を一気に進めない）。
   - この要素は `touch-action: none` にして、ページのスクロール・ピンチとぶつからないようにする（タスク5のジェスチャーの抑制と整合）。
   - **タップでも回せるまま残す**（なぞるのが苦手な人・片手・支援技術のため）。キーボード・読み上げ用の「1タップで1回転」ボタンも残す。
   - 動きを減らす設定（reduced motion）ではハンドルの回転アニメを控えめにし、操作は同じ。
   - 確定までコインは減らない、などの既存の決まりは変えない。
3. テスト: 角度の積み上げの単体テスト（1周で1回、半周では進まない、逆回し、速すぎる入力、指が外れたとき）、画面テスト（なぞりで1回転進む・タップでも進む）、E2E（Playwright で pointer を円に動かして3回転 → 開封へ。Chromium と WebKit）。UX の44px 以上の押せる範囲を保つ。`docs/ux-reviews/<task>.json` を作る。
4. 文書: PRODUCT.md（回し方）、ADOPTED_DESIGN.md（マスターの変更履歴）、STATUS.md。
5. PR → CI 緑 → Bot のマージ → 本番公開 → 担当者に URL と QR（実機で「丸くなぞって回す」を確認してもらう）。

**完了の条件**: 回す画面で、ハンドルを指で丸く1周なぞるたびに1回転進み、3回転で開封に進む。タップ・ボタンでも今までどおり回せる。iPhone と Android の実機で、なぞってもページがスクロール・拡大しない。
