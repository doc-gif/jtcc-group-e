# UI/UX マージ基準

調査日: 2026-09-25。基準バージョン: 1。

Apple HIG の原則をモバイル Web に適用し、キャラクターや着せ替えを中心とするゲームの事例から、楽しさ・安心感・自己表現の評価軸を追加する。これは本プロジェクトの必須チェックであり、Apple による認証や、すべての女性向けゲームに共通する規格ではない。好みを性別だけで決めず、対象利用者の反応で検証する。

## 調査根拠と採用判断

## 必須項目

| ID | 合格条件 | 自動確認／エージェント確認 |
| --- | --- | --- |
| HIG-01 | 本文の標準は 17 CSS px、補助文でも読める大きさを保つ。通常文字は 4.5:1、大きな文字は WCAG AA の 3:1 を満たす。状態を色だけで伝えない | axe の WCAG AA 検査＋重要文言・画像内文字・色依存を目視確認 |
| HIG-02 | 操作領域 44×44 CSS px 以上。重要操作を誤って押さない間隔にする。アイコン操作には名前を付け、タッチ以外の操作でも到達できる | DOM の表示サイズ、axe、主要フローのキーボードテスト＋タッチ位置を確認 |
| HIG-03 | 320px 幅、縦横、文字サイズ 200% で目的を達成できる。ノッチ・ホームバーに重要内容が重ならない。文字の拡大（OS・ブラウザの文字サイズ）と OS の拡大鏡を妨げず、viewport の `maximum-scale`・`user-scalable=no` で拡大を禁止しない（画面全体のピンチ拡大だけは担当者の決定で止める。F16、[PRODUCT.md](PRODUCT.md)） | レスポンシブ・文字拡大テスト＋セーフエリアの CSS／実機確認。CI のエミュレーターは実機のノッチを再現しない |
| HIG-04 | 目的と次の操作が分かる。戻る／閉じる／キャンセルが一貫する。フォーカス移動、入力ラベル、エラーの説明がある | axe と操作シナリオ＋情報の優先順位・空状態・失敗時の回復を確認 |
| HIG-05 | Reduce Motion を尊重し、装飾の反復・拡大縮小を抑える。音だけに情報を依存せず、勝手に音を鳴らさない。演出が操作を妨げない | reduced-motion・自動再生検査＋JS／Canvas の演出とスキップ手段を確認 |
| GAME-01 | 配色・余白・形・言葉・キャラクター表現に一貫性があり、装飾より主要な操作や内容が認識できる | 実画面のスクリーンショットとデザイン意図をエージェントが照合 |
| GAME-02 | 操作の結果が分かり、失敗時は責める文言を使わず回復できる。保存や確定を誤認させない | 正常／待機／失敗の操作テスト＋フィードバックの文言と演出を確認 |
| GAME-03 | 自分のペースで中断・再開できる。強制通知・過剰なバッジ・不利益をちらつかせる誘導を増やさない | 継続・中断のシナリオと通知方針を確認。該当機能がなければ理由を記録 |
| GAME-04 | 着せ替え・推し・選択肢がある場合、選ぶ楽しさと変更／取消を保つ。公開や共有の範囲が明確 | 試着・変更・取消・公開範囲のシナリオ。実装していない機能は理由付き対象外 |
| GAME-05 | 初回の説明が短く、必要な時に補足できる。利用者の好みを決めつけず、やさしく具体的な言葉を使う | 初見で目的を説明できるか、専門用語・強制チュートリアル・決めつけをエージェントが確認 |

## マージの仕組み

`UI/UX gate` は必須ステータスチェック。ブラウザ検査に加え、現在の UI のダイジェストに一致するレビュー記録を要求する。記録のない UI 変更、古い記録、`fail`、`pending`、説明のない対象外は失敗する。Bot はこのゲートと `Quality gate` の両方が成功した PR だけを承認する。

世界観や文言の良さを CI が自動で理解するわけではない。実装担当エージェント／作業者が画面を見て判断し、CI はその記録の網羅性・鮮度と機械検証できる条件を確かめる。レビューの誠実さや実際の利用者の満足まで自動テストでは保証しない。

## UI を変更する作業者の手順

1. `e2e/ux-scenarios.ts` に変更した画面と状態を追加する。画面遷移・入力・保存などの利用者の目的を E2E でも検証する。
2. `pnpm build`、`pnpm exec playwright test ux.spec.ts` を実行する。HTML レポートのスクリーンショットを開き、変更画面・文字拡大・待機／空／失敗状態を確認する。iOS 固有の変更は実機確認の結果も書く。
3. 全 10 項目を確認し、`pnpm ux:digest` で現在のダイジェストを取得する。
4. `docs/ux-reviews/<task-name>.json` に reviewer、summary、uiDigest、criteria を保存する。各項目は `id`、`result`（`pass` または `not-applicable`）、20文字以上の `evidence` を持つ。証拠はテスト名、画面、確認した挙動を具体的に書く。
5. 画面を見ずに digest だけ更新しない。対象外は「機能が未実装」等の理由を書く。適用される基準の不合格を対象外として扱わない。
6. `pnpm verify` に成功してから Ready にする。

基準自体の変更も UI のダイジェストに含む。これにより、基準を緩める変更にも新たな記録を要求する。過去のレビュー JSON は保持する。
