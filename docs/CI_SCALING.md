# テストと開発速度を規模に合わせる

## 現在の構成

1. Preview build は独立して動き、短い検証後に URL・QR を先行配布する。
2. 全体 CI は型・lint・単体・ビルドを1回実行し、同じ成果物を全ブラウザジョブで共有する。
3. Playwright の全テストを実行前に列挙し、件数から分割数を決定する。現在105件は4分割。
4. 各分割を別の GitHub Actions runner で並行実行する。通常・拡大・アクセシビリティ・動きを減らす設定・全5構成は削減しない。
5. blob report をまとめ、検出件数と合格件数の一致を確認する。欠落・失敗・skip・flaky は不合格。
6. `Quality gate` と `UI/UX gate` は成功した全体結果を必須にする。UIレビュー記録も別途必須。片方の成功だけでマージしない。

## 自動で増える分割

[`.github/ci-settings.json`](../.github/ci-settings.json) が設定の入口。

| 設定 | 初期値 | 意味 |
| --- | --- | --- |
| targetTestsPerShard | 30 | 1分割の目安件数 |
| maxShards | 8 | 自動分割の上限 |
| maxParallel | 4 | 同時に使うブラウザ runner 数 |
| workersPerShard | 2 | 各 runner 内の並列数 |
| warnBrowserSeconds | 180 | ブラウザジョブの長時間化を警告する秒数 |

105件なら4分割、210件なら7分割。並列上限を超えた分は待機する。上限に達してもテストを省略せず全件実行する。設定が不正なら停止する。無制限に runner を増やしたり、課金枠を変更したりしない。

`Complete browser reports` の Summary に分割ごとの所要秒数を記録し、目安を超えると警告する。長時間化はまず遅いシナリオ・無駄な待機・テストデータの衝突・セットアップ時間を調べる。それでも不足する場合に並列枠と分割数を調整する。実行枠と予算が有限なので、規模が増えても時間が絶対に増えない保証ではない。

## デグレを防ぐ集約

`fail-fast: false` により1件の失敗で他の分割を途中終了せず、失敗箇所をまとめて調べられる。必須ゲートは `always()` で動き、前段の failure / cancelled / skipped を成功扱いにしない。

新しい `.spec.ts` を `e2e/` に追加すると、全体 CI のテスト列挙・分割対象に自動で入る。手動でテスト名や件数を更新する方式ではない。失敗を再実行で偶然通す運用をせず、原因を修正する。

`browser-reports` に統合 HTML と JSON、`quality-reports` にカバレッジ・検出一覧・分割計画、`blob-<番号>` に分割ごとのスクリーンショットとトレースを14日保存する。

## プロダクトが大きくなるときの開発ルール

- 計算・入力検証・状態遷移は純粋な関数と単体テストを中心にする。画面の細部をすべて E2E の組合せで増やさない。
- E2E は主要な利用目的、重要な失敗・保存・復元・モバイル操作を担当する。新機能は単体→部品→主要フローの順で検証を置く。
- 共有状態や外部サービスを前提にしたテストを避け、テストごとにデータとブラウザ context を分離する。将来 API を追加するときはテストデータの名前空間も分割ごとに分ける。
- 小さい PR と専用 worktree を維持し、共通ファイル・ロックファイルを複数人で同時に変更しない。大きい画面を1ファイルへ集約せず、機能・状態・共通部品で責務を分ける。
- ローカルは変更した層のテストで早くフィードバックを得る。最終的な全件検証は CI と並行し、同じ SHA の成功を何度も取り直さない。
- モノレポ化した場合は依存関係が追跡できる単位でビルド・単体テストのキャッシュを導入する。依存関係が不明なまま path filter で品質ゲートをスキップしない。現在は全件検証を維持する。
