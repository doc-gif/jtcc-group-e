## 実 DB で確認したこと（2026-09-26）

この作業環境からは `*.supabase.co` に HTTP で接続できない（プロキシが `CONNECT` を 403 で拒否）。そのため、ブラウザの流れと同じ RPC を、Supabase MCP の SQL で `authenticated` ロールと JWT の `sub`（匿名ユーザー `is_anonymous: true` と同じ形）を切り替えて順に呼び、最後に例外で取り消した（1 つの DO ブロック）。ホスト用キーは担当者の本物のキーを使わず、使い捨てのキー（salt とハッシュだけ）をその取引の中で入れて取り消した。担当者のキーの行（`owner 2026-09`）は読んでいない・変えていない。

## 起床通知（Realtime、#68）

- ルームの状態が変わる RPC（`lp_join`・`lp_ready`・`lp_leave`・`lp_start`・予約の開始と取り消し・予約の時刻での開始／開始できなかったこと・ピッチモード・`lp_rename`・`lp_resume_host`）が、取引の中で `realtime.send` を 1 回呼ぶ。非公開チャンネル `lp:<roomId>`、イベント `round`、内容は `{roomId, roundNo, reason}` だけ（名前・キー・招待コード・結果・ユーザー ID を入れない）。取り消された RPC は送らない。
- 受け取れるのは、そのルームの active な参加者・ホストだけ（`realtime.messages` の SELECT ポリシー `lp_receive_round` → `lp_can_receive`）。クライアントからの送信（INSERT）は許さない。
- 受け取った端末は内容を使わず `lp_snapshot` を取り直す。ポーリング（15 秒）はそのまま残す。購読の状態は状態層の `realtime`（`live`／`polling`）に持ち、切れてからつながり直したときは一度取り直す。
- migration と実 DB での確認: [SQL_MIGRATION_68.md](SQL_MIGRATION_68.md)。

## 使うときの注意（ピッチの前に）

- **入室・準備・退室・「今すぐ開始」・予約・名前の変更は、ほかの端末に数秒で届く**（#68 の Realtime の起床通知）。「今すぐ開始」でも参加者の 8 秒の秒読みがそろう。Realtime に入れない端末（回線・社内のプロキシなど）は、今までどおり 15 秒ごとのポーリングで取り直す（その端末だけ最大 15 秒遅れる）。予約開始もそのまま使える。
- **無料プランの Realtime の上限**: 同時接続 200・イベント 100 件/秒（ほかの端末へ届けた通知 1 件ずつを数える）。100 人のルームでは 1 回の変化で 100 件になるので、全員がいっせいに準備すると上限を超え、Supabase が接続をいったん切る（supabase-js が自動でつなぎ直し、その間はポーリングで動く）。多人数で使う前に担当者の判断（#68）。
- **匿名ログインは 1 つの IP から 1 時間に 60 回まで**（T12 の設定）。会場の Wi‑Fi のように全員が同じ回線だと、61 人目以降が入れない。人数が多いときは、各自のモバイル回線で開いてもらうか、担当者が Dashboard（Authentication → Rate Limits）で上限を上げる（担当者の判断）。
- 本番・確認用プレビューの URL ごとに別の匿名 ID になる。ホストと参加者は同じ URL（招待リンク）を使う。
- 本番に出すのは取りまとめ役の指示のとき（[DEPLOYMENT.md](DEPLOYMENT.md)）。

1. `main`（`f71d9ae`）の開発サーバーを、コミットしない `.env.local` で同じ Supabase につないだもの。
2. この PR の確認用プレビュー（run `36220390928`、SHA `e9a283c`）の `app/`。CI の成果物そのもので、本番の公開にも同じ成果物を使う。

ホスト用キーは担当者のキーを使わず、ローカル検証用のキー（ラベル `local test 2026-09-26`、`lp_host_keys` には salt とハッシュだけ）を別に登録した。検証で作ったルームは終えるたびに `expires_at = now()` で閉じ、キーは本番の確認が終わったら `revoked_at` で無効にする。

### 気づいた点（この PR では直していない）

- ホストが別の端末で再開したあとの元の端末は、「ルームは終了しました」「招待が無効か、期限が切れています」「新しいルームを作る」と出る。実態は「ホストが別の端末に移った」なので文言が違い、元の端末から新しいルームを作れてしまう。マスターにこの状態の画面はないため、担当者の判断（Figma を先に直す）を待つ。
- （当時）ロビーの人数・準備の反映は 15 秒のポーリングで、操作によっては 30 秒ほど待った。#68 で数秒になった。

## 担当者の 2 台での確認手順（5 分）

用意: スマホ 2 台（A＝担当者、B＝参加者）。できれば 3 台目（C）。ルームの開始にはホストのほかに 2 人が必要（F13）。2 台だけのときは、B のほかに同じスマホの別のブラウザ（例: Safari と Chrome）を C にする。

0. （F16、ルームの確認とは別）各スマホで確認用の URL を開く。ブラウザのタブで開いた街ホームの地図の下に「ホーム画面に追加すると、全画面で遊べます」の案内が出ることを見る（#57。Android の Chrome では「ホーム画面に追加」のボタンが出ることがある）。案内の手順で**ホーム画面に追加**し、ホーム画面のアイコンから開く（iPhone: Safari の共有 →「ホーム画面に追加」。Android: Chrome のメニュー →「ホーム画面に追加」または「アプリをインストール」）。リンクバーが出ないこと、ピンチで画面が拡大しないこと、画面の端から横にスワイプしても前の画面に戻らないこと、上から引っぱっても再読み込みしないこと、ボタンを長押ししてもメニューが出ないこと、OS の文字サイズを大きくすると文字が大きくなること、ホーム画面のアプリでは案内が出ないことを見る。ブラウザに戻って案内の「閉じる」を押すと、再読み込みしても出ないこと。ホーム画面のアプリには招待リンクを開く場所がなく、iPhone では保存データも Safari と別なので、下の 1〜7 のルームの確認は今までどおりブラウザで行う（ホーム画面のアプリで入る方法は未決。[PRODUCT.md](PRODUCT.md) の未決事項）。
1. A でホスト用リンク `https://<確認用プレビューまたは本番の URL>/#/host/<キー>` を開く。アドレスバーから `#/host/…` のキーが消え、「ルームを作る」が出る（「デモ：…」の注記が出ないこと）。名前を入れて「ルームを作る」。
2. A の「招待リンクを共有」→「リンクをコピー」で招待リンクを B（と C）へ送る。
3. B で招待リンクを開き「ルームに入る」→ 名前（例「ゆい」）→ 入る。A の画面の「集まっている人」が 15 秒以内に 2 人になること。B で「抽選に参加する」。
4. C で同じ招待リンクを開き、「ルームに入る」→「名前を決めずに入る」→ 自動の名前（例「ゲスト さくら12」）で入る。A に「あと N 人」が消え、「開封をはじめる」が押せること。
5. A で「開始の時間を予約する」→「1分後」→「1分後に開始を予約」。B・C にも予約の秒読みが出ること。時刻になると 3 台とも「もうすぐ開封！」の秒読み → 「せーので、ひらこう！」→ 結果。B の「みんなの結果を見る」に、A・B（と参加した人）の結果が同じ内容で出ること。
6. B で再読み込み（または一度アプリを閉じて招待リンクを開き直す）→ 同じルームの結果・ロビーに戻ること。
7. うまくいかないときは、画面の文言と時刻、使った URL（キーは送らない）を取りまとめ役に伝える。

## ピッチでの「ホーム画面に追加」の案内（#57）

- 来場者には、まず LP・QR から開いたブラウザのタブで街ホームを見てもらう。地図の下の案内（iPhone: 共有ボタン →「ホーム画面に追加」、Android: メニュー →「ホーム画面に追加」、または案内の「ホーム画面に追加」ボタン）で追加すると、次からはリンクバーのない全画面で開ける。追加しなくても遊べるので、急がせない。
